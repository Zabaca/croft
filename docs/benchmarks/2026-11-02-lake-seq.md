# The log's order number in a lake (D145)

`scripts/bench-lake-seq.ts`, run on 2026-11-02 on macOS arm64 (bun 1.3.14, DuckDB 2.0.0, Postgres 17 and an S3-compatible store started by the test rig, all on this machine), 25 log rows per step, medians of 7 steps per cell. A step is one write transaction, from BEGIN to COMMIT; the per-INSERT figures take the cost of an empty transaction off.

- "subquery" is how the log adapter numbered a row until slice 2 of lake mode: `(SELECT coalesce(max(seq), 0) FROM log) + 1` inside each INSERT.
- "adapter" is `bookkeepingOf(tx).upsert(...)` as it is now: the highest number is read once per transaction and table into a connection variable, and the rows are numbered from that.
- The 20 ms and 60 ms round-trip rows put the same Postgres behind a TCP proxy that holds every chunk back 10 ms or 30 ms in each direction. A simulation of distance, not a measurement of a real network or of R2; it keeps the order of the bytes and nothing else (no loss, no jitter, no bandwidth limit).

What it shows:

- On this machine the subquery costs 2.4 to 3.0 ms an INSERT, flat in the size of the log from 0 to 20,000 rows, in SQLite and in Postgres alike, as D132 measured. It is the distance that makes it slow: at a 20 ms round trip it is about 104 ms an INSERT (about five round trips), at 60 ms about 275 ms, against 10 and 25 ms for the adapter. A write that makes a dozen bookkeeping INSERTs spends over a second on the number at 20 ms and over three at 60 ms with the subquery, and 0.1 and 0.3 s without.
- The adapter's own statements (a read of a variable, a SET VARIABLE, and the INSERT) cost a local lake about 0.6 ms an INSERT more than numbering from a number the client already has (0.9 ms in the first run of this script, with the raw variant), and are the same at any distance.
- Not what this is about, but it is in the table: an empty write transaction costs 770 ms at a 20 ms round trip and 2.1 s at 60 ms, about 38 round trips, against 10 ms here. That is DuckLake's BEGIN and COMMIT against its catalog, not croft's statements, and it is paid by every write step whatever it writes. A remote lake wants a nearby catalog.
